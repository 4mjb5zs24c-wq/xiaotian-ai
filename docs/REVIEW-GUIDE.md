# 技术评审流程与讲评指南

> 本文档帮助你了解如何组织一次高效的技术评审会议，以及如何在会上讲好你的项目。

---

## 一、评审前准备

### 1.1 提前 1-2 天发给评审人员

| 材料 | 说明 |
|------|------|
| 线上地址 | https://resonant-sprinkles-1bdde7.netlify.app |
| 评审文档 | `docs/REVIEW.md` |
| 核心路由 | `/` `/vocabulary-insight` `/writing-insight` `/search` |

### 1.2 准备好演示环境

- [ ] 浏览器打开线上地址，清空缓存
- [ ] 打开"小天助手"抽屉备用
- [ ] 提前走一遍核心流程，确保不卡顿
- [ ] 准备好切换数据范围的演示

### 1.3 明确评审目标

技术评审的核心目标是回答三个问题：

| 问题 | 怎么回答 |
|------|---------|
| 做完了吗？ | 对照需求清单逐项确认 |
| 做得对吗？ | 交互流程是否闭环、数据边界是否覆盖 |
| 能上线吗？ | 有没有阻塞问题，后续还需要做什么 |

## 二、评审会议流程（建议 45-60 分钟）

### 第一阶段：项目概览（5 分钟）

**你来讲：**
1. 本期交付范围：AI 词汇洞察 + AI 写作洞察 + AI 搜索闭环 + 首页优化
2. 基于 `feature/writing-insight` 分支，相比 main 新增 54 个文件
3. 全部使用 Mock 数据，未对接后端

**评审方关注点：**
- "改了多少？动没动老代码？"
- 你回答：修改了 10 个已有文件（App路由、HomePage、Store等），其余 54 个是新文件，未改 P0 冻结规则

---

### 第二阶段：功能演示（25 分钟）

**按以下路径走，边操作边讲：**

#### 1. 首页（3 分钟）
```
打开首页 → 指给评审看教学关注卡片（词汇洞察、写作洞察、阶段性报告）
→ 点击词汇洞察卡片 → 进入词汇洞察页
→ 返回首页 → 点击写作洞察卡片 → 进入写作洞察页
```

#### 2. 词汇洞察（8 分钟）
```
词汇洞察页 → 讲一下页面结构（侧边导航 + 6 个模块）
→ 切换数据范围（7天/14天/30天）
→ 悬浮错误类型分布流，展示 tooltip
→ 点击错词展开典型错误详情
→ 勾选错词 → 底部操作栏出现 → 点击词汇复习规划
→ 走完 4 步向导：选目标 → 设周期 → 设词量+回滚+掌握判定 → 生成方案
→ 展示干预记录的效果对比
```

#### 3. 写作洞察（8 分钟）
```
写作洞察页 → 页面结构（侧边导航 + 8 个模块）
→ 悬浮问题类型分布流
→ 展开高频写作问题，展示学生原句→问题说明→修改建议→优化示例
→ 点击薄弱学生 → 右侧抽屉详情
→ 优秀作文 → 点击作为范文参考
→ AI 诊断卡 → 生成范文 → 3 篇范文对比
→ 推荐写作资源 → 加入试卷篮
```

#### 4. AI 搜索（6 分钟）
```
AI 搜索页 → 输入"Unit 1 资源" → 展示搜索结果
→ 输入"同步词汇" → 展示内容选择 → 勾选词 → 选练习形式 → 生成练习 → 布置确认
→ 输入"词汇听写" → 展示功能入口（只有一个，不出现其他）
→ 输入"山东省中考真题" → 试卷搜索结果
→ 输入"abc123" → 展示无结果 + 快捷入口
→ 点击试卷篮 → 打开练习篮查看已加入的资源
```

### 第三阶段：技术细节讨论（15 分钟）

**你来说：**

| 技术点 | 说明 |
|------|------|
| **状态管理** | Zustand 全局 store，paperBasket 做了 localStorage 持久化 |
| **搜索匹配** | 规则引擎，8 级优先级匹配，15 种场景覆盖 |
| **分布流组件** | 从 10 种格式（A-J）中经过实际对比选定的 J 格式 |
| **侧边导航** | IntersectionObserver 自动追踪可视区块，不依赖滚动事件 |
| **Mock 数据** | 词汇 14 场景 + 写作 13 场景 + 搜索 15 场景，覆盖正常/边界/异常 |

**评审方可能问的问题及你的回答：**

| 问题 | 回答 |
|------|------|
| "为什么不用真实数据？" | 后端 API 还没好，Mock 先验证交互流程。Mock 结构已对齐预期接口字段，切换成本低 |
| "性能怎么样？" | Bundle 约 1MB，后续可以做代码分割优化 |
| "有测试吗？" | 目前没有单元测试，交互原型阶段。后续 P1 补充 |
| "手机上看过吗？" | 面向 PC 教师端，未做移动端适配，侧边导航 < 1280px 自动隐藏 |
| "老功能受影响吗？" | 原有路由/页面未改动，P0 冻结规则（Intent路由、Drawer行为、Preview/Assign/Basket）均未动 |
| "作文订正去哪了？" | 一期 Mock 阶段暂未实现，已经在后续规划中（P3） |

---

### 第四阶段：总结与后续（5 分钟）

**你来总结：**

1. **已交付**：词汇洞察 + 写作洞察 + AI 搜索闭环 + 首页优化
2. **不交付**（一期明确不做的）：导出、自由问答、作文讲评、作文订正、写作提升方案
3. **已知问题**：全部 Mock 数据、无单元测试、无 CI/CD
4. **下一步**：P0 对接后端 API → P1 测试+CI/CD → P2 响应式

**评审方确认：**
- "同意合并到 main？"
- "后续优先级有没有调整？"
- "有没有阻塞需要我协调的？"

## 三、讲评技巧

### 3.1 讲功能不念代码

```
❌ "我在这个组件里写了 useState，然后用 filter 函数..."
✅ "老师点击错词类型标签，下面的列表会自动筛选出对应类型的错词"
```

### 3.2 先演示核心路径，再补充边界

```
1. 先走完"首页→洞察页→复习方案→干预记录"这条完整链路（证明功能闭环）
2. 再展示空状态、无结果、切换数据范围 这些边界情况
3. 最后才讲技术细节
```

### 3.3 提前预演 2-3 遍

最容易出问题的地方：
- "生成练习"按钮点了没反应（可能忘了选内容或练习形式）
- 搜索框输入后要按回车
- 试卷篮是空的看起来像 bug

### 3.4 遇到 Bug 怎么办

```
"这个我记下来，会后修" —— 不用当场改，别卡住流程
"这个是已知限制，一期 Mock 阶段暂不支持" —— 主动说出来
```

### 3.5 让评审方动手试试

核心路径走完后，把鼠标交给评审方，让他们自己点 2-3 分钟。他们的操作习惯会暴露出你没考虑到的交互问题。

## 四、评审常见评价及应对

| 评价 | 应对 |
|------|------|
| "交互太复杂了，老师不会用" | 展示侧边导航和搜索入口，说明做了引导 |
| "数据对不上" | 说明是 Mock，强调 mock 结构和真实接口一致 |
| "为什么不先做移动端？" | 本期需求明确是 PC 教师端，移动端在 P2 |
| "少了 XXX 功能" | 对照需求清单确认是否在一期范围 |
| "这个颜色/间距不好看" | 记下来，不争论，会后按优先级修 |

## 五、评审后跟进

### 5.1 评审纪要

会后立即写下来：
- 评审参与人
- 通过 / 有条件通过 / 不通过
- 修改意见清单（每条标注优先级）
- 下次评审时间（如有需要）

### 5.2 修改意见模板

```
# 评审修订记录
- [ ] P0: XXX 功能白屏，需紧急修复
- [ ] P1: XXX 组件颜色与设计稿不符
- [ ] P2: XXX 交互流程可优化
- [ ] P3: 建议增加 XXX 过渡动画
```

### 5.3 合并与发布

| 步骤 | 操作 |
|------|------|
| 1 | 按评审意见修改代码 |
| 2 | 重新 `npm run build` + `npx netlify deploy` |
| 3 | 通知评审方复审 |
| 4 | 通过后合入 main |
| 5 | 打 tag / 标记版本 |
